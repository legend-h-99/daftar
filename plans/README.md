## Security audit findings considered and rejected (2026-07-09, commit a82de24)

- **SEC-01** (`jwtService.decode()` throws on malformed input): `decode()` returns `null`, not throws; `if (!jti) return` guard is correct — not a bug.
- **SEC-07** (decode on unverified token in logout): logout is behind `JwtAuthGuard`, so token is already signature-verified before `decode()` is called — not a vulnerability.
- **SEC-06** (Prisma parameterization missing in OCR upsert): all DB calls use Prisma's structured query API (`findFirst`, `create`, `update`) — no raw SQL, no injection surface.
- **SEC-08** (XSS in material name display): React escapes all JSX expressions by default; no `dangerouslySetInnerHTML` in the codebase — not a finding.
- **SEC-10** (invoice number Int32 overflow): Prisma `Int` = 32-bit signed integer = 2.1 billion max; exceeds any plausible invoice volume — not a real risk.
- **SEC-11** (phone normalization bypass): the `@Body()` DTO validates `phone` with `@IsPhoneNumber()` before it reaches `normalizePhone()` — not exploitable.
- **SEC-13** (glob/picomatch/tmp CVEs): all are dev-only transitive dependencies, not present in production runtime — not a risk.
- **SEC-14** (SQL injection via Prisma raw queries): no `$queryRaw` or `$executeRaw` calls in the codebase — not a finding.

## Original audit findings considered and rejected

The following findings from the audit were explicitly evaluated and not planned:

- **CORRECTNESS-01** (number Int vs string): JS numeric coercion handles DB integers cleanly — not a real bug.
- **CORRECTNESS-02** (issueDate null): schema has `DateTime @default(now())` NOT NULL — near-zero risk; not worth a plan.
- **CORRECTNESS-03/05** (paidAmount null): schema has `Float @default(0)` NOT NULL; dashboard only queries UNPAID/PARTIAL; Prisma ignores undefined fields — not a real bug.
- **SEC-06** (enum validation): `FindInvoicesQueryDto` already has `@IsEnum(InvoiceStatus)` — confirmed not a finding.
- **SEC-07/DEBT-03** (forbidNonWhitelisted false): `whitelist: true` strips extra fields; silent stripping is lower risk than false rejections in an Arabic-RTL mobile app.
- **SEC-08** (general rate limiting): 100 req/min global throttle is appropriate for MVP scale.
- **SEC-10** (JWT localStorage): documented MVP decision in `apps/web/lib/auth.ts` comment; httpOnly cookie migration is pre-v1 work, not planned here.
- **SEC-13** (IDOR pattern): code is consistently safe; flagged for future developer guidance, not a fix.
- **SEC-15** (CSRF): mitigated by SEC-02 fix (CORS plan 002); no separate plan needed.
- **SEC-14** (security logging): low priority for MVP; not planned.
- **DEBT-01** (find-or-throw pattern): real tech debt but pure refactor, low urgency.
- **DEBT-02** (missing GET :id on customers/suppliers): S effort, low impact — considered not worth a plan at this time; can be done inline with any customer/supplier feature work.
- **DEBT-04** (PDF in service): works correctly; extraction is a quality-of-life refactor; not planned.
- **DEBT-06** (constants duplication): trivial cleanup; not planned.
- **DEPS-02** (env config validation): low priority; the CORS startup guard in plan 002 covers the most critical gap.
- **PERF-04** (stock movements pagination): MED confidence, not a growing risk in current data model.
- **DIR-02** (invoice OCR): valid direction suggestion but not planned yet.
- **DIR-03/04/05** (bulk export, dedup, audit trail): post-MVP scope.

## Unplanned high-value direction

- **SMS gateway** (DIR-01): Cannot onboard real users without it. Ship blocker. Requires choosing a Saudi SMS provider (Unifonic, Taqnyat, or Twilio with ME numbers), adding credentials to env, and implementing the TODO at `auth.service.ts:67`. Recommend planning this immediately after plan 002.
- **Server-side month filtering for invoices/purchases** (DEBT-05 / PERF finding 6): Invoices and purchases pages fetch all records then filter client-side. Add `month` query param to `/invoices` and `/purchases` endpoints. Medium effort, plan when scale is felt.
- **JWT revocation** (SEC-04): 30-day tokens with no logout mechanism. Medium effort — add `TokenBlacklist` table or switch to refresh-token pattern before public launch.
